# LLM IDE Change Log / Decision Log v0.1

## 1. 문서 목적

이 문서는 LLM IDE 개발 과정에서 발생한 주요 결정과 변경 이력을 기록한다.

목적은 다음과 같다.

* 왜 구조가 바뀌었는지 기록한다.
* 어떤 결정이 현재 기준선에 반영되었는지 추적한다.
* Codex 개발 기준이 흔들리지 않도록 한다.
* 향후 변경 시 과거 의사결정의 맥락을 확인할 수 있게 한다.

이 문서는 다음 두 영역으로 구성한다.

```text
Decision Log
- 제품 방향, 아키텍처, 원칙에 대한 결정 기록

Change Log
- 문서 버전별 변경 내역 기록
```

## DEC-001. API 기반 IDE로 새로 구축한다

### 결정

기존 구현을 전환하거나 유지하지 않고, API 기반 프로젝트 상태 관리 IDE를 새로 구축한다.

### 배경

초기 기준에서 사용 가능한 애플리케이션 소스는 없었다.
따라서 기존 구현을 고치기보다, 새 구조를 기준으로 설계하는 것이 적절했다.

### 결정 내용

```text
프로젝트 상태는 IDE가 기억한다.
AI는 매 요청마다 필요한 맥락을 주입받아 실행된다.
```

### 영향

* LLM 장기 세션에 의존하지 않는다.
* Project Runtime이 장기성을 담당한다.
* 맥락 빌더가 핵심 엔진이 된다.

* `LlmIde.Wpf`는 후속 UI 계층이 된다.

```text

- conversations/conversation.db
```

* request_id가 SQLite와 JSONL/JSON 기록을 연결한다.
* conversation_turns, conversation_messages, context_packages를 사용한다.
* 추가 전용 로그도 유지한다.

## DEC-013. 장기 대화 관리는 요약 + 창를 기본 전략으로 한다

### 결정

LLM IDE의 기본 맥락 관리 전략은 `요약 + 창`다.

```text
원본 대화 로그
+ 롤링 맥락 요약
+ 최근 대화 창
```

### 채택 알고리즘

| 알고리즘                        | 적용 여부 | 역할                         |
| --------------------------- | ----: | -------------------------- |
| Sliding Window              | 부분 채택 | 최근 대화 창 구현           |
| Conversation Summary Buffer |    채택 | 롤링 맥락 요약 생성 |
| 요약 + 창            | 기본 전략 | 장기 대화 관리                   |
| Session-based RAG           |    보류 | File Store 이후 검토           |

### 영향

* 과거 전체 대화 원문은 매 요청에 넣지 않는다.
* 과거 맥락은 롤링 맥락 요약로 주입한다.
* 최근 대화는 제한된 원문 윈도우로 주입한다.
* 현재 사용자 요청은 항상 원문으로 주입한다.

### 상태


## DEC-015. Compression 실패는 Chat 실패가 아니다

### 결정

압축 요청가 실패해도 사용자 chat 응답은 유지한다.

### 실패 처리

```text
사용자 응답 성공
원본 대화 로그 저장 성공
압축 요청 실패
```

결과:

* 사용자 응답 유지
* 원본 사용자 / AI 메시지 유지
* 기존 `current.md` 유지
* 요청 로그에 실패 기록
* 다음 chat은 기존 Summary 사용

### 금지 사항

* Compression 실패 때문에 사용자 응답을 폐기하지 않는다.
* 원본 대화 로그를 롤백하지 않는다.
* 빈 Summary로 current.md를 덮어쓰지 않는다.

### 상태

```text
확정
```

## DEC-036. 대화 저장 ID는 프로젝트별 순번 기반으로 생성한다

### 결정

신규 conversation request_id와 message_id는 GUID 기반 문자열 대신 프로젝트별 숫자 순번 문자열로 생성한다.

```text
request_id: 1, 2, 3, 4 ...
message_id: 1, 2, 3, 4 ...
```

### 배경

GUID 기반 ID는 고유성은 높지만 사람이 대화 저장 순서를 확인하기 어렵다.

## DEC-046. Agent Loop와 fetch_url 도구 도입

## DEC-049. Agent Loop는 Project Runtime의 하위 실행 루프로 둔다

### 결정

Agent Loop는 Project Runtime의 하위 실행 루프로 둔다.
Agent Loop는 사용자의 단일 Request를 처리하기 위한 내부 실행 절차이며, 독립된 별도 런타임이 아니다.

### 경계 원칙 (Agent Boundary Principle 재확인)

* Agent Loop는 Project, Criteria, Project State, Artifact를 직접 변경하지 않는다.
* Agent Loop는 허용된 ToolHost 도구만 호출할 수 있다.
* MVP의 도구는 읽기 전용(read-only) 도구로 제한한다. (`fetch_url`, `web_search`)
* 상태 변경, 기준 변경, 산출물 확정, 파일 수정, 외부 실행은 사용자 승인 없이는 수행할 수 없다.

### 위치 정리

* 입력 1회 → Agent Loop(LLM·도구 다회차) → 최종 응답까지가 하나의 Request 처리 단위다.
* 도구 디스커버리와 감독 allowlist는 [[DEC-048]]을 따른다.
* 도구 도입·보안 기준은 [[DEC-046]], [[DEC-047]]을 따른다.
* 로드맵 상 위치는 Phase 8.5 (Agent Loop v1 - Search and Fetch Tools)다.

### 상태


## DEC-050. 에이전트 도구 호출 로그 기록 위치

### 결정

채팅 중 실행된 에이전트 도구 호출을 전용 로그에 영속 기록한다.
도구 호출은 대화 메시지(messages)와 분리해, 맥락 주입에 섞이지 않도록 한다.

### 결정 내용

* 기록 위치
  * JSONL: `<ProjectRoot>/.llmide/conversations/tool-calls.jsonl`
  * SQLite: `conversation.db`의 `agent_tool_calls` 테이블
* 기록 항목: `requestId`(채팅 요청 ID), `sequence`(요청 내 실행 순서), `tool`, `target`, `ok`, `resultSummary`, `errorMessage`, `createdAt`.
* 보안([[DEC-046]] 재확인): `target`에는 시크릿을 남기지 않는다.
  * `fetch_url`은 전체 URL이 아니라 host만 기록한다. (query string 시크릿 노출 방지)
  * `web_search`는 검색어(query)를 기록한다.
  * 본문 원문은 남기지 않고 요약(상태코드/문자수/결과 개수 등)만 남긴다.
* 도구 호출 로그는 `GetRecentMessages`/최근 대화 창 주입 대상이 아니다. (맥락 오염 방지)
* `list_tools` 도구 목록 조회도 기록한다. 나중에 모델의 의도를 파악할 수 있도록 디스커버리 단계를 남긴다.
  * `tool`="list_tools", `target`=제공된 도구 이름 목록, `resultSummary`=`tools=N`.

### 완전성 보장 (누락 금지)

도구 사용 기록은 하나도 빠짐없이 남긴다.

* 도구 목록 조회(list_tools)와 도구 실행을 모두, 실행 순서대로 같은 순번(`sequence`) 체계로 기록한다.
* 실행된 도구는 성공/실패와 무관하게 모두 기록한다. (예외로 실패한 실행도 실패 결과로 기록)
* 모든 실행 경로가 기록한다.
  * 채팅(`ChatService`): 매 단계(조회/실행) 직후 기록.
  * 에이전트 루프(`AgentLoop` / CLI `agent-run`): 조회+실행을 순서대로 담은 `AgentRunResult.ToolCalls`를 `agent` 요청 ID로 묶어 기록. 도구 실행 예외도 포함되어 누락되지 않는다.
* 기록 변환은 `ConversationToolCallRecord.Create`로 일원화해 경로별 차이를 없앤다.

## DEC-057. 진단 로깅 도입 (SystemLog [Info]/[Debug])

### 결정

LLM에 실제로 주입되는 내용과 도구 입출력을 검증할 수 있도록, 감독 제공 로컬 라이브러리 `Framework.Common`의 파일 로거로 진단 로그를 남긴다.

### 배경

기존에는 LLM에 무엇이 주입되는지(맥락 패키지는 요약), 도구가 외부와 무엇을 주고받았는지(`tool-calls.jsonl`은 요약, [[DEC-050]]) 전체 데이터를 확인할 수 없었다. "빈 응답"·"도구 결과 0개" 같은 문제 진단에 원본 데이터가 필요했다.

### 결정 내용

* `Framework.Common.Logger.Log` 싱글턴으로 `<작업폴더>/Log/SystemLog_yyyyMMdd.log`에 한 줄당 1건(compact JSON)으로 기록한다.
* `[Info]` = 실제 LLM 호출. 호출 직전 메시지 배열 전체(주입 프롬프트)와 원본 응답(빈 문자열 포함), 모델/스트리밍 여부/소요시간/에러. 채팅 3개 호출 지점(일반/스트리밍/압축)을 모두 기록한다.
* `[Debug]` = 도구 입출력 전체. arguments 전체와 result 전체(요약·자르기 없음), ok/error/소요시간.
* 레이어 분리: Core에 `ILlmRequestLogger`/`IToolIoLogger`(+Null 구현), Infrastructure에 `FrameworkCommon*` 구현. ChatService에 주입.
* 가독성: 도구 프로토콜 JSON(`AgentJson`)과 로그 직렬화는 비-ASCII를 escape하지 않는다(`UnsafeRelaxedJsonEscaping`). 한글이 로그·모델 양쪽에서 그대로 보이고, 모델에 전달되는 도구 결과도 깔끔해진다.

### 비고

* `tool-calls.jsonl`(요약, [[DEC-050]])은 그대로 유지하고, 전체 데이터는 SystemLog `[Debug]`로 분리한다.
* `Framework.Common`은 NuGet이 아니라 `package/Lib.Net10/`의 로컬 DLL을 참조한다(아키텍처 기준 라이브러리 목록 반영). 라이브러리의 TCP 모듈은 향후 Local Server 단계에서 사용 가능.


### 배경

모델이 한 응답에 여러 도구를 쓰려고 `tool_request` JSON을 여러 개 따로 출력하면 단일-객체 파서가 깨졌다. 모델 성향(여러 검색 동시 시도)에 맞춰 배열을 정식 형식으로 받는 게 안정적이다.

### 결정 내용

* 프로토콜: `{"type":"tool_request","requests":[{"tool":..,"arguments":{..}}, ..]}`. 도구가 하나여도 배열에 담는다. 지시문(`chat_tool_instruction`)이 배열 형식과 스키마를 강제한다.
* 파서는 배열을 파싱하되, 모델이 옛 단일 형식을 내도 1개짜리 배열로 변환한다(안전망).
* 실행: 배열을 `Task.WhenAll`로 동시 실행하고, 결과는 요청 순서대로 모아 `{"type":"tool_result","results":[..]}` 한 메시지로 보낸다.
* 부분 실패 허용: 알 수 없는 도구·예외는 해당 항목의 에러 결과로 담고 나머지는 계속한다. 각 실행은 도구 호출 로그([[DEC-050]])와 tool I/O 로그([[DEC-057]])에 모두 남는다.
* 적용 범위: 채팅(ChatService). AgentLoop(CLI `agent-run`)는 기존 단일 형식 유지(파서는 호환).

## DEC-060. 모델 응답 JSON 추출을 "첫 균형 객체"로 견고화한다

### 결정

모델 응답에서 프로토콜 JSON을 추출할 때, "첫 `{` ~ 마지막 `}`"가 아니라 **첫 번째 완전한 균형(balance-matched) JSON 객체**를 추출한다.

### 배경

모델이 JSON 끝에 `}`를 하나 더 붙이거나(예: deepseek-v4-pro), `<tool_call>` 같은 태그로 감싸거나, 객체를 여러 개 출력하면, 기존 추출이 여분 문자를 포함해 파싱이 실패했다. 파싱 실패는 "도구 아님 = 최종답"으로 처리되어 도구 호출이 통째로 버려졌다.

### 결정 내용

* 첫 `{`부터 중괄호 깊이를 추적하고, 문자열 내부의 `{}`·`"`(이스케이프 포함)는 무시하며, depth가 0이 되는 첫 객체에서 멈춘다. 그 뒤의 여분 `}`·후속 객체·래퍼 태그·프로즈는 버린다.
* 정상 JSON 동작은 그대로 두고 malformed만 복구한다. 진짜 비-JSON은 여전히 실패(ModelError)한다.
* AgentLoop·ChatService 양쪽에 자동 적용된다.

## DEC-061. web_search는 DuckDuckGo에 POST로 요청한다

### 결정

`web_search`의 DuckDuckGo HTML 검색을 GET 쿼리스트링이 아니라 form-urlencoded POST로 요청한다.

### 배경

DuckDuckGo HTML 엔드포인트는 GET을 차단해 HTTP 202와 결과 없는 페이지를 반환했고(파싱 결과 0개, `ok=true`로 표기됨), POST는 200과 실제 결과 마크업을 반환했다.

### 결정 내용

* `HttpMethod.Post` + `FormUrlEncodedContent`(`q=<query>`)로 변경. 파싱(결과 앵커/스니펫 정규식)은 유지.
* 테스트는 가짜 HTTP 핸들러를 사용해 외부를 호출하지 않는다(메서드 무관).

### 비고

검색 품질·키 기반 엔진(Google Custom Search / Brave) 또는 WebView2 기반 렌더링 검색 전환은 v0.6 후보로 둔다(미결).
