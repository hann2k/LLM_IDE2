# Phase 1. 프로젝트 초기화 및 프로젝트 목록 관리

## 목표

프로젝트를 영어 `pID` 기반으로 초기화하고, 사용자 표시 이름 `name`은 별도로 저장한다.
IDE 프로그램 하부의 고정 프로젝트 저장소에서 프로젝트 목록을 관리한다.

## 구현 항목

* IDE 프로그램 루트 확인
* `<IdeProgramRoot>/project` 폴더 생성
* `<IdeProgramRoot>/project/projects.json` 생성
* 프로젝트 `pID` 필수 처리
* 빈 `pID` 입력 시 `DefaultProject`로 처리
* 기존 `DefaultProject` 중복 생성 차단
* 중복 오류 시 파일 저장 및 폴더 생성 금지
* 프로젝트 `pID` 중복 확인
* 프로젝트 `pID`는 영문자로 시작하고 영문자, 숫자, `-`, `_`만 허용
* 사용자 표시 이름 `name` 별도 저장
* 경로 미지정 시 `<IdeProgramRoot>/<ProjectPId>` 생성
* 경로 지정 시 지정 경로에 프로젝트 폴더 생성
* 프로젝트 `pID`, 사용자 표시 이름, 경로, 생성일자 저장
* 프로젝트 사용자 표시 이름 수정
* 프로젝트 `pID` 수정
* 프로젝트 경로 수정
* `.llmide` 폴더 생성
* `init-progress.json` 생성 및 단계별 진행 상태 기록
* 기본 설정 파일 생성
* `project.json` 생성
* `project-state.json` 생성
* `criteria.json` 생성
* `<IdeProgramRoot>/policies/` 기본 정책 템플릿 생성
* 신규 프로젝트 생성 시 `.llmide/policies/system-rule.md` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/compression-rule.md` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/artifact-rule.md` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/importance-rule.md` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/context-policy.json` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/provider-policy.json` 기본값 생성
* 프로젝트 목록 조회
* 프로젝트 `pID`로 열기
* 프로젝트 `pID`로 목록에서 제거
* 프로젝트 `pID`로 실제 프로젝트 폴더 삭제
* 실제 프로젝트 폴더 삭제 시 프로젝트 `pID` 재확인 강제
* API Key가 있는 프로젝트 삭제 시 추가 확인 강제
* 권한 오류 표시 및 중단
* 옵션 없이 실행 시 사용법 출력
* CLI 명령 구현

## CLI 예시

```bash
llmide
llmide init
llmide init --pid MyProject
llmide init --pid MyProject --name "내 프로젝트"
llmide init --path /Users/me/Projects/DefaultProject
llmide init --pid MyProject --name "내 프로젝트" --path /Users/me/Projects/MyProject
llmide projects list
llmide projects open MyProject
llmide projects remove MyProject
llmide projects delete MyProject --confirm MyProject
llmide projects delete MyProject --confirm MyProject --confirm-api-key-delete
llmide projects rename MyProject "새 표시 이름"
llmide projects repid MyProject NewProjectId
llmide projects move MyProject /Users/me/Projects/NewPath
```

## 완료 기준

* `pID` 없이 초기화하면 `DefaultProject`로 해석된다.
* 기존 `DefaultProject`가 없는 경우 `DefaultProject`가 생성된다.
* 기존 `DefaultProject`가 있는 상태에서 `pID` 없이 초기화하면 오류를 표시하고 중단한다.
* 중복 오류에서는 파일 저장과 폴더 생성이 발생하지 않는다.
* 경로 없이 초기화하면 `<IdeProgramRoot>/<ProjectPId>` 아래에 프로젝트 데이터가 생성된다.
* `pID`, 표시 이름, 경로를 모두 지정하면 `pID`와 표시 이름은 고정 프로젝트 저장소에 등록되고 데이터는 지정 경로에 생성된다.
* 프로젝트 저장소에는 `pID`, 표시 이름, 경로, 생성일자가 저장된다.
* 프로젝트 `pID`, 표시 이름, 경로를 수정할 수 있다.
* 프로젝트 목록은 `pID` 기준으로 조회된다.
* 기존 프로젝트를 `pID`로 열 수 있다.
* `remove`는 프로젝트 저장소 목록에서만 제거하고 실제 프로젝트 폴더는 삭제하지 않는다.
* `delete`는 실제 프로젝트 폴더를 삭제하고 프로젝트 저장소 목록에서도 제거한다.
* `delete`는 `--confirm <project-id>` 없이는 실행되지 않는다.
* 프로젝트에 API Key가 있으면 `delete`는 `--confirm-api-key-delete` 없이는 실행되지 않는다.
* 권한 오류가 발생하면 오류를 표시하고 초기화를 중단한다.
* 프로젝트 폴더 생성 후 실패한 경우 `init-progress.json`에서 실패 단계를 확인할 수 있다.
* 옵션 없이 실행하면 사용법이 출력된다.
* 사용법에는 가능한 명령 조합이 출력된다.
* IDE 재실행 후에도 프로젝트 `pID`와 표시 이름 목록이 유지된다.

## 상태

```text
완료
```

# Phase 3. 대화 로그 저장

## 목표

모든 대화를 프로젝트에 저장한다.

SQLite를 프로젝트 단위 주 저장소로 사용하고, JSONL/JSON 파일은 보조 기록, 디버깅, 요청 재현용으로 유지한다.

## 구현 항목

* `.llmide/conversations/conversation.db` 생성
* SQLite `conversation_turns` 테이블 저장
* SQLite `conversation_messages` 테이블 저장
* SQLite `context_packages` 테이블 저장
* `messages.jsonl` 저장
* `requests.jsonl` 저장
* 요청별 맥락 패키지 저장
* chat 명령 실행 시 사용자 메시지 저장
* chat 명령 응답 수신 시 assistant 메시지 저장
* 다음 chat 명령 실행 시 SQLite에 저장된 최근 사용자/AI 메시지 주입
* 요청 재현을 위한 `request_id` 연결
* SQLite 기록과 JSONL/JSON 보조 기록이 같은 `request_id`를 공유하도록 처리

## 완료 기준

* 프로젝트 초기화 시 `.llmide/conversations/conversation.db`가 생성된다.
* 사용자 메시지와 AI 응답이 저장된다.
* 사용자 메시지와 AI 응답이 SQLite의 같은 conversation turn에 연결된다.
* 요청별 맥락 패키지가 SQLite와 JSON 파일 양쪽에 저장된다.
* 두 번째 이후 대화는 이전 사용자/AI 메시지를 포함해 Provider API에 요청한다.
* 어떤 맥락으로 응답이 생성되었는지 추적 가능하다.
* `conversation_turns`, `conversation_messages`, `context_packages`가 `request_id`로 연결된다.
* `messages.jsonl`, `requests.jsonl`, `context-packages/<request_id>.json`이 서로 같은 `request_id`로 연결된다.
* 신규 대화 저장 시 request_id와 message_id는 프로젝트별 순번 기반으로 생성되어 저장 순서를 사람이 확인할 수 있다.
* 신규 chat request record에는 LLM이 평가한 `importance_weight`가 `0~10` 범위로 저장된다.

## CLI 예시

```bash
llmide criteria add MyProject --title "Korean" --description "항상 한국어로 답한다" --priority high
llmide criteria list MyProject
llmide criteria update MyProject <criterion-id> --description "한국어를 기본으로 사용한다"

```

## 완료 기준

* 활성 기준이 API 요청에 포함된다.
* 활성 기준은 system 메시지로 Provider 요청에 포함된다.
* 비활성 기준은 Provider 요청에 포함되지 않는다.
* 활성 기준이 하나도 없으면 Provider API로 전송하지 않고 중단한다.
* Criteria를 생성, 조회, 수정, 삭제할 수 있다.
* Criteria를 활성화, 비활성화할 수 있다.
* 요청별 맥락 패키지에서 사용된 활성 기준을 확인할 수 있다.
* 요청 로그에서 사용된 기준을 확인할 수 있다.

# Phase 6. Rolling Context Compression

## 목표

장기 대화 맥락을 롤링 맥락 요약로 관리한다.

압축은 LLM Provider API를 이용한다.
원본 대화 로그와 압축 맥락을 분리해 저장한다.

## 구현 항목

* `conversations/rolling-context/` 폴더 생성
* `rolling-context/current.md` 생성
* `rolling-context/history/` 생성
* `rolling-context/index.jsonl` 생성
* `policies/compression-rule.md` 생성
* `context-policy.json` 압축 정책 확장
* SQLite `rolling_context_summaries` 테이블 추가
* chat 응답 이후 압축 요청 실행
* 롤링 맥락 요약가 없는 최초 compression에서는 누적 원본 대화 로그 전체를 압축
* 이전 Summary와 현재 사용자/AI 대화를 병합
* debug 모드에서는 압축 요청 입력을 먼저 출력하고 Compression 응답을 스트리밍으로 출력
* 새 Summary를 `history/`에 저장
* `current.md` 갱신
* 기존 Summary를 `superseded` 상태로 기록
* 압축 요청를 Request Log에 별도로 기록
* Compression 실패 시 기존 Summary 유지

## 완료 기준

* chat 이후 롤링 맥락 요약가 생성된다.
* 다음 chat 요청에 `current.md`가 포함된다.
* 원본 대화 로그는 삭제되거나 덮어써지지 않는다.
* 압축 요청가 일반 채팅 요청와 구분되어 기록된다.
* 압축 요청의 실제 provider messages를 debug와 context package로 확인할 수 있다.
* 스트리밍 chat debug에서 Compression 응답 진행 상태를 chunk 단위로 확인할 수 있다.
* Compression 실패 시 사용자 응답은 정상 유지된다.
* Compression 실패 시 기존 Summary가 유지된다.

완료

# Phase 7. 맥락 빌더 v1

* 활성 기준 주입

# Phase 8. 산출물 저장

## 목표

중요한 응답을 재사용 가능한 산출물로 저장한다.

AI 응답 중 보존 가치가 있는 내용을 명시 태그 기반 산출물 후보로 분리한다.
C# 코드는 자연어 의미를 추측하지 않고, 명시 태그가 붙은 영역만 추출한다.

## 설계 원칙

* chat 요청에는 `.llmide/policies/artifact-rule.md` 내용을 읽어 “답변 중 중요한 산출물 후보에는 산출물 태그를 붙이라”는 지시를 포함한다.
* 산출물 태그 형식은 구현 시점에 결정하되, MVP에서는 사람이 읽을 수 있고 파싱이 단순한 형식을 우선한다.
* 태그가 붙은 내용은 저장 후보일 뿐이며, 사용자 승인 없이 확정 저장하지 않는다.
* 원본 chat 응답은 그대로 대화 로그에 남긴다.
* 산출물 저장은 Agent Boundary Principle을 따른다.
* 산출물 태그 요청 문구는 코드 내부에 두지 않고 정책 파일로 관리한다.
* 신규 프로젝트 생성 시 `<IdeProgramRoot>/policies/`의 기본 정책 템플릿 전체를 `<ProjectRoot>/.llmide/policies/`로 복사한다.

## 구현 항목

* 산출물 태그 지시를 `policies/artifact-rule.md`에서 읽어 맥락 빌더가 주입
* 산출물 태그 파서 구현
* 산출물 후보 추출
* 산출물 생성
* 산출물 수정
* 산출물 목록 조회
* 산출물 첨부
* CLI 관리 명령 구현

## CLI 명령

```bash

llmide artifacts show <project-id> <artifact-id>
llmide artifacts add <project-id> --title <title> --type <type> --content <content>
llmide artifacts add <project-id> --title <title> --type <type> --file <file-path>
llmide artifacts update <project-id> <artifact-id> --title <title>
llmide artifacts update <project-id> <artifact-id> --content <content>
llmide artifacts remove <project-id> <artifact-id>

```

## 완료 기준

* CLI가 태그가 붙은 산출물 후보를 추출할 수 있다.
* 응답을 산출물로 저장할 수 있다.

* 태그가 없는 일반 응답은 산출물로 자동 분류하지 않는다.
* 사용자 승인 없이 산출물를 확정 저장하지 않는다.

# Phase 8.5. Agent Loop v1 - Search and Fetch Tools

## 목표

사용자의 단일 Request를 처리하기 위해 LLM과 도구가 다회차로 주고받는 내부 실행 루프(Agent Loop)를 구현한다.
MVP에서는 읽기 전용 검색/조회 도구(`web_search`, `fetch_url`)만 제공한다.

## 위치 및 경계 (DEC-049)

Agent Loop는 Project Runtime의 하위 실행 루프다.

```text
사용자 Request 1회
→ Agent Loop (LLM ↔ ToolHost 다회차)
→ 최종 응답
= Request 처리 단위
```

* Agent Loop는 사용자의 단일 Request를 처리하기 위한 내부 실행 절차다.
* Agent Loop는 Project, Criteria, Project State, Artifact를 직접 변경하지 않는다.
* Agent Loop는 허용된 ToolHost 도구만 호출할 수 있다.
* MVP의 도구는 읽기 전용 도구로 제한한다.
* 상태 변경, 기준 변경, 산출물 확정, 파일 수정, 외부 실행은 사용자 승인 없이는 수행할 수 없다.

## 실행 흐름 (DEC-048)

```text
0 사용자 발화
→ 1 LLM이 list_tools 요청
→ 2 IDE가 가용 도구 목록(tool_list) 제공
→ 3 LLM tool_request
→ 4 IDE 도구 실행 및 결과(tool_result) 제공
→ 5 LLM 정리·완료 판단 (3부터 반복)
→ 6 final 종료
```

## 구현 항목

* Core: `IAgentLoop`/`AgentLoop`, `IChatModelClient`, `IAgentTool`/`IAgentToolHost`/`AgentToolHost`
* Core: 모델(AgentTurn, AgentToolRequest/Result, AgentRunRequest/Result, StopReason, AgentLoopOptions)
* 프로토콜: `list_tools` / `tool_list` / `tool_request` / `tool_result` / `final` (AgentProtocol, AgentMessageParser)
* 도구 자기기술: `Name` / `Description` / `Arguments`
* 도구: `fetch_url`(SSRF 차단), `web_search`(키 없는 DuckDuckGo HTML)
* 도구 등록·필터 일원화: `AgentToolHostFactory`
* 감독 allowlist: 전역 `<IdeProgramRoot>/settings/agent-tools.json`
* DeepSeek 어댑터: `DeepSeekChatModelClient`
* CLI: `agent-run` 명령
* 채팅 통합: `ChatService`가 동일 프로토콜로 도구 호출, WPF는 도구 단계 라벨 표시

## 보안 기준 (DEC-046)

* 허용 스킴 http/https, 차단 file/ftp/data/javascript 등
* 차단 호스트/대역: localhost, 0.0.0.0, 루프백, 사설망, link-local, unique-local, 빈/과장 URL
* 응답 크기·문자 수·리다이렉트·타임아웃 제한
* 로그에는 전체 URL/시크릿을 남기지 않고 host 정도만 남긴다
* 도구 실패는 앱을 죽이지 않고 실패 ToolResult로 반환한다
* 테스트는 실제 외부 URL을 호출하지 않는다 (가짜 HTTP 핸들러 사용)

## 완료 기준

* 사용자 단일 Request에서 LLM과 도구가 다회차로 주고받아 최종 답변을 만든다.
* LLM은 URL을 직접 열지 않고 도구를 통해서만 외부에 접근한다.
* 도구 목록은 list_tools 디스커버리로 제공되고, 감독이 전역 allowlist로 제한할 수 있다.
* 도구는 읽기 전용이며, 상태/기준/산출물/파일을 직접 변경하지 않는다.
* CLI `agent-run`과 WPF 채팅 모두 Agent Loop를 사용한다.
* 빌드 경고 0/오류 0, 테스트 전체 통과.

### Codex 작업 015. 대화 저장 ID 순번화

목표:

* 대화 저장 ID를 GUID 기반 값에서 프로젝트별 순번 기반 값으로 변경한다.

요구사항:

* request_id는 저장 순서대로 `1`, `2`, `3`, `4` 형태로 증가한다.
* message_id는 저장 순서대로 `1`, `2`, `3`, `4` 형태로 증가한다.
* JSONL, SQLite, context package 파일명이 같은 request_id를 공유한다.
* 기존 GUID 기반 기록은 유지하고, 신규 숫자 ID 생성 시 숫자 ID만 순번 계산에 사용한다.

완료 기준:

* 첫 chat 요청은 request_id `1`로 저장된다.
* 첫 chat 후 compression 요청은 request_id `2`로 저장된다.
* 첫 user 메시지는 message_id `1`로 저장된다.
* 첫 assistant 메시지는 message_id `2`로 저장된다.
* 이후 대화는 기존 숫자 ID의 다음 순번으로 저장된다.

### Codex 작업 016. 대화 중요도 가중치 저장

목표:

* chat 응답에서 현재 대화의 중요도를 LLM에게 평가받고 대화 데이터에 저장한다.

요구사항:

* `importance_weight` 값 범위는 `0~10`이다.
* 숫자가 커질수록 중요도가 높다.
* 중요도 측정 명령은 코드 상수가 아니라 `policies/importance-rule.md` 파일에 둔다.
* 신규 프로젝트 생성 시 `.llmide/policies/importance-rule.md`를 생성한다.
* chat 요청에 importance rule을 system 메시지로 포함한다.
* LLM 응답의 명시 태그에서 중요도를 파싱한다.
* 파싱한 중요도를 chat request record에 저장한다.

완료 기준:

* `conversation_turns`와 `requests.jsonl`의 chat request record에 `importance_weight`가 저장된다.
* 중요도 태그가 없거나 파싱할 수 없으면 `0`으로 저장된다.
* compression request의 기본 중요도는 `0`이다.
* 중요도 측정 프롬프트 문구는 `importance-rule.md` 파일에서 관리된다.

* 사용자는 표시 이름 `name`을 자유롭게 지정하고 수정할 수 있다.
* 기존 CLI 명령은 `pID`로 프로젝트를 찾는다.

## 7. MVP 완료 기준

MVP는 다음 조건을 만족해야 한다.

* 긴 대화에서도 과거 전체 원문을 매 요청에 포함하지 않는다.
* 과거 맥락은 롤링 맥락 요약로 전달한다.
* 최근 대화는 최근 대화 창로 전달한다.
* 롤링 맥락 요약는 LLM Provider API를 통해 생성한다.
* 원본 대화 로그와 압축 맥락은 별도로 보존한다.
* Compression 실패 시 원본 대화과 사용자 응답은 유지한다.
* 각 요청에서 어떤 압축 맥락이 사용되었는지 추적할 수 있다.
* `요약 + 창`를 기본 맥락 관리 전략으로 사용한다.
* 프로젝트 상태를 저장하고 요청에 포함할 수 있다.
* Criteria를 저장하고 요청에 포함할 수 있다.
* 산출물를 저장하고 요청에 첨부할 수 있다.
* CLI와 WPF는 동일한 Core를 사용할 수 있다.
* WPF에서 현재 Core/CLI 기반 기능을 사용할 수 있다.
* Context Notes를 저장하고 요청에 포함할 수 있다.
* File Store를 통해 파일을 명시적으로 요청에 첨부할 수 있다.
* State Update Candidate는 사용자 승인 후에만 적용된다.
* Server는 후속 어댑터 계층으로 Core를 호출할 수 있다.
