# LLM IDE Development Roadmap v0.1

## 1. 문서 목적

이 문서는 LLM IDE의 개발 단계를 관리하기 위한 실행 로드맵이다.

이 문서는 다음을 다룬다.

* MVP 개발 순서
* Phase별 목표
* Phase별 구현 항목
* Phase별 완료 기준
* 현재 진행 상태
* 다음 작업
* 후속 확장 계획

제품 원칙과 아키텍처 기준은 별도 문서에서 관리한다.

# Phase 1. 프로젝트 초기화 및 프로젝트 목록 관리

## 목표

프로젝트를 영어 `pID` 기반으로 초기화하고, 사용자 표시 이름 `name`은 별도로 저장한다.
IDE 프로그램 하부의 고정 프로젝트 저장소에서 프로젝트 목록을 관리한다.

## 구현 항목

* IDE 프로그램 루트 확인
* `<IdeProgramRoot>/project` 폴더 생성
* `<IdeProgramRoot>/project/projects.json` 생성
* 프로젝트 `pID` 필수 처리
* 빈 `pID` 입력 시 `DefaultProject`로 처리
* 기존 `DefaultProject` 중복 생성 차단
* 중복 오류 시 파일 저장 및 폴더 생성 금지
* 프로젝트 `pID` 중복 확인
* 프로젝트 `pID`는 영문자로 시작하고 영문자, 숫자, `-`, `_`만 허용
* 사용자 표시 이름 `name` 별도 저장
* 경로 미지정 시 `<IdeProgramRoot>/<ProjectPId>` 생성
* 경로 지정 시 지정 경로에 프로젝트 폴더 생성
* 프로젝트 `pID`, 사용자 표시 이름, 경로, 생성일자 저장
* 프로젝트 사용자 표시 이름 수정
* 프로젝트 `pID` 수정
* 프로젝트 경로 수정
* `.llmide` 폴더 생성
* `init-progress.json` 생성 및 단계별 진행 상태 기록
* 기본 설정 파일 생성
* `project.json` 생성
* `project-state.json` 생성
* `criteria.json` 생성
* `<IdeProgramRoot>/policies/` 기본 정책 템플릿 생성
* 신규 프로젝트 생성 시 `.llmide/policies/system-rule.md` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/compression-rule.md` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/artifact-rule.md` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/importance-rule.md` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/context-policy.json` 기본값 생성
* 신규 프로젝트 생성 시 `.llmide/policies/provider-policy.json` 기본값 생성
* 프로젝트 목록 조회
* 프로젝트 `pID`로 열기
* 프로젝트 `pID`로 목록에서 제거
* 프로젝트 `pID`로 실제 프로젝트 폴더 삭제
* 실제 프로젝트 폴더 삭제 시 프로젝트 `pID` 재확인 강제
* API Key가 있는 프로젝트 삭제 시 추가 확인 강제
* 권한 오류 표시 및 중단
* 옵션 없이 실행 시 사용법 출력
* CLI 명령 구현

## CLI 예시

```bash
llmide
llmide init
llmide init --pid MyProject
llmide init --pid MyProject --name "내 프로젝트"
llmide init --path /Users/me/Projects/DefaultProject
llmide init --pid MyProject --name "내 프로젝트" --path /Users/me/Projects/MyProject
llmide projects list
llmide projects open MyProject
llmide projects remove MyProject
llmide projects delete MyProject --confirm MyProject
llmide projects delete MyProject --confirm MyProject --confirm-api-key-delete
llmide projects rename MyProject "새 표시 이름"
llmide projects repid MyProject NewProjectId
llmide projects move MyProject /Users/me/Projects/NewPath
```

## 완료 기준

* `pID` 없이 초기화하면 `DefaultProject`로 해석된다.
* 기존 `DefaultProject`가 없는 경우 `DefaultProject`가 생성된다.
* 기존 `DefaultProject`가 있는 상태에서 `pID` 없이 초기화하면 오류를 표시하고 중단한다.
* 중복 오류에서는 파일 저장과 폴더 생성이 발생하지 않는다.
* 경로 없이 초기화하면 `<IdeProgramRoot>/<ProjectPId>` 아래에 프로젝트 데이터가 생성된다.
* `pID`, 표시 이름, 경로를 모두 지정하면 `pID`와 표시 이름은 고정 프로젝트 저장소에 등록되고 데이터는 지정 경로에 생성된다.
* 프로젝트 저장소에는 `pID`, 표시 이름, 경로, 생성일자가 저장된다.
* 프로젝트 `pID`, 표시 이름, 경로를 수정할 수 있다.
* 프로젝트 목록은 `pID` 기준으로 조회된다.
* 기존 프로젝트를 `pID`로 열 수 있다.
* `remove`는 프로젝트 저장소 목록에서만 제거하고 실제 프로젝트 폴더는 삭제하지 않는다.
* `delete`는 실제 프로젝트 폴더를 삭제하고 프로젝트 저장소 목록에서도 제거한다.
* `delete`는 `--confirm <project-id>` 없이는 실행되지 않는다.
* 프로젝트에 API Key가 있으면 `delete`는 `--confirm-api-key-delete` 없이는 실행되지 않는다.
* 권한 오류가 발생하면 오류를 표시하고 초기화를 중단한다.
* 프로젝트 폴더 생성 후 실패한 경우 `init-progress.json`에서 실패 단계를 확인할 수 있다.
* 옵션 없이 실행하면 사용법이 출력된다.
* 사용법에는 가능한 명령 조합이 출력된다.
* IDE 재실행 후에도 프로젝트 `pID`와 표시 이름 목록이 유지된다.

# Phase 3. 대화 로그 저장

## 목표

모든 대화를 프로젝트에 저장한다.

SQLite를 프로젝트 단위 주 저장소로 사용하고, JSONL/JSON 파일은 보조 기록, 디버깅, 요청 재현용으로 유지한다.

## 구현 항목

* `.llmide/conversations/conversation.db` 생성
* SQLite `conversation_turns` 테이블 저장
* SQLite `conversation_messages` 테이블 저장
* SQLite `context_packages` 테이블 저장
* `messages.jsonl` 저장
* `requests.jsonl` 저장
* 요청별 맥락 패키지 저장
* chat 명령 실행 시 사용자 메시지 저장
* chat 명령 응답 수신 시 assistant 메시지 저장
* 다음 chat 명령 실행 시 SQLite에 저장된 최근 사용자/AI 메시지 주입
* 요청 재현을 위한 `request_id` 연결
* SQLite 기록과 JSONL/JSON 보조 기록이 같은 `request_id`를 공유하도록 처리

## 완료 기준

* 프로젝트 초기화 시 `.llmide/conversations/conversation.db`가 생성된다.
* 사용자 메시지와 AI 응답이 저장된다.
* 사용자 메시지와 AI 응답이 SQLite의 같은 conversation turn에 연결된다.
* 요청별 맥락 패키지가 SQLite와 JSON 파일 양쪽에 저장된다.
* 두 번째 이후 대화는 이전 사용자/AI 메시지를 포함해 Provider API에 요청한다.
* 어떤 맥락으로 응답이 생성되었는지 추적 가능하다.
* `conversation_turns`, `conversation_messages`, `context_packages`가 `request_id`로 연결된다.
* `messages.jsonl`, `requests.jsonl`, `context-packages/<request_id>.json`이 서로 같은 `request_id`로 연결된다.
* 신규 대화 저장 시 request_id와 message_id는 프로젝트별 순번 기반으로 생성되어 저장 순서를 사람이 확인할 수 있다.
* 신규 chat request record에는 LLM이 평가한 `importance_weight`가 `0~10` 범위로 저장된다.

# Phase 4. Criteria 관리

## 목표

프로젝트 기준을 저장하고 요청에 주입한다.

## 구현 항목

* Criteria 생성
* Criteria 수정
* Criteria 삭제
* Criteria 활성화
* Criteria 비활성화
* `criteria.json` 저장
* 활성 기준 주입
* 요청별 맥락 패키지에 활성 기준 기록
* 활성 기준가 없으면 chat 요청 중단
* CLI 관리 명령 구현

## CLI 예시

```bash
llmide criteria add MyProject --title "Korean" --description "항상 한국어로 답한다" --priority high
llmide criteria list MyProject
llmide criteria update MyProject <criterion-id> --description "한국어를 기본으로 사용한다"
llmide criteria deactivate MyProject <criterion-id>
llmide criteria activate MyProject <criterion-id>
llmide criteria remove MyProject <criterion-id>
```

## 완료 기준

* 활성 기준이 API 요청에 포함된다.
* 활성 기준은 system 메시지로 Provider 요청에 포함된다.
* 비활성 기준은 Provider 요청에 포함되지 않는다.
* 활성 기준이 하나도 없으면 Provider API로 전송하지 않고 중단한다.
* Criteria를 생성, 조회, 수정, 삭제할 수 있다.
* Criteria를 활성화, 비활성화할 수 있다.
* 요청별 맥락 패키지에서 사용된 활성 기준을 확인할 수 있다.
* 요청 로그에서 사용된 기준을 확인할 수 있다.

# Phase 6. Rolling Context Compression

## 목표

장기 대화 맥락을 롤링 맥락 요약로 관리한다.

압축은 LLM Provider API를 이용한다.
원본 대화 로그와 압축 맥락을 분리해 저장한다.

## 구현 항목

* `conversations/rolling-context/` 폴더 생성
* `rolling-context/current.md` 생성
* `rolling-context/history/` 생성
* `rolling-context/index.jsonl` 생성
* `policies/compression-rule.md` 생성
* `context-policy.json` 압축 정책 확장
* SQLite `rolling_context_summaries` 테이블 추가
* chat 응답 이후 압축 요청 실행
* 롤링 맥락 요약가 없는 최초 compression에서는 누적 원본 대화 로그 전체를 압축
* 이전 Summary와 현재 사용자/AI 대화를 병합
* debug 모드에서는 압축 요청 입력을 먼저 출력하고 Compression 응답을 스트리밍으로 출력
* 새 Summary를 `history/`에 저장
* `current.md` 갱신
* 기존 Summary를 `superseded` 상태로 기록
* 압축 요청를 Request Log에 별도로 기록
* Compression 실패 시 기존 Summary 유지

## 완료 기준

* chat 이후 롤링 맥락 요약가 생성된다.
* 다음 chat 요청에 `current.md`가 포함된다.
* 원본 대화 로그는 삭제되거나 덮어써지지 않는다.
* 압축 요청가 일반 채팅 요청와 구분되어 기록된다.
* 압축 요청의 실제 provider messages를 debug와 context package로 확인할 수 있다.
* 스트리밍 chat debug에서 Compression 응답 진행 상태를 chunk 단위로 확인할 수 있다.
* Compression 실패 시 사용자 응답은 정상 유지된다.
* Compression 실패 시 기존 Summary가 유지된다.

# Phase 7. 맥락 빌더 v1

## 목표

요청에 필요한 맥락을 조립한다.

압축된 롤링 맥락 요약와 현재 발화 중심의 요청 조립을 적용한다.

## 구현 항목

* 시스템 규칙 주입
* 활성 기준 주입
* 프로젝트 상태 주입
* 롤링 맥락 요약 주입
* 최근 대화 창는 현재 MVP에서 `0`으로 기록
* 수동 첨부 필드 예약
* 산출물 필드 예약
* 맥락 패키지 생성
* 요청별 사용된 `rolling_context_id` 기록
* 최근 대화 포함 개수와 문자 수 제한 적용

## 완료 기준

* 요청마다 맥락 패키지가 생성된다.

# Phase 8. 산출물 저장

## 목표

중요한 응답을 재사용 가능한 산출물로 저장한다.

AI 응답 중 보존 가치가 있는 내용을 명시 태그 기반 산출물 후보로 분리한다.
C# 코드는 자연어 의미를 추측하지 않고, 명시 태그가 붙은 영역만 추출한다.

## 설계 원칙

* chat 요청에는 `.llmide/policies/artifact-rule.md` 내용을 읽어 “답변 중 중요한 산출물 후보에는 산출물 태그를 붙이라”는 지시를 포함한다.

* 산출물 저장은 Agent Boundary Principle을 따른다.
* 산출물 태그 요청 문구는 코드 내부에 두지 않고 정책 파일로 관리한다.

# Phase 8.5. Agent Loop v1 - Search and Fetch Tools

## 목표

사용자의 단일 Request를 처리하기 위해 LLM과 도구가 다회차로 주고받는 내부 실행 루프(Agent Loop)를 구현한다.
MVP에서는 읽기 전용 검색/조회 도구(`web_search`, `fetch_url`)만 제공한다.

## 위치 및 경계 (DEC-049)

Agent Loop는 Project Runtime의 하위 실행 루프다.

```text
사용자 Request 1회
→ Agent Loop (LLM ↔ ToolHost 다회차)
→ 최종 응답
= Request 처리 단위
```

* Agent Loop는 사용자의 단일 Request를 처리하기 위한 내부 실행 절차다.
* Agent Loop는 Project, Criteria, Project State, Artifact를 직접 변경하지 않는다.
* Agent Loop는 허용된 ToolHost 도구만 호출할 수 있다.
* MVP의 도구는 읽기 전용 도구로 제한한다.
* 상태 변경, 기준 변경, 산출물 확정, 파일 수정, 외부 실행은 사용자 승인 없이는 수행할 수 없다.

## 실행 흐름 (DEC-048)

```text
0 사용자 발화
→ 1 LLM이 list_tools 요청
→ 2 IDE가 가용 도구 목록(tool_list) 제공
→ 3 LLM tool_request
→ 4 IDE 도구 실행 및 결과(tool_result) 제공
→ 5 LLM 정리·완료 판단 (3부터 반복)
→ 6 final 종료
```

## 구현 항목

* Core: `IAgentLoop`/`AgentLoop`, `IChatModelClient`, `IAgentTool`/`IAgentToolHost`/`AgentToolHost`
* Core: 모델(AgentTurn, AgentToolRequest/Result, AgentRunRequest/Result, StopReason, AgentLoopOptions)
* 프로토콜: `list_tools` / `tool_list` / `tool_request` / `tool_result` / `final` (AgentProtocol, AgentMessageParser)
* 도구 자기기술: `Name` / `Description` / `Arguments`
* 도구: `fetch_url`(SSRF 차단), `web_search`(키 없는 DuckDuckGo HTML), `read_file`(프로젝트 폴더 내 읽기, 경로 탈출 차단), `list_files`(프로젝트 폴더 내 폴더/파일 목록, `.llmide` 제외), `artifacts_list`/`read_artifact`(아티팩트 목록·조회, ArtifactService 경유)
* 도구 등록·필터 일원화: `AgentToolHostFactory`
* 감독 allowlist: 전역 `<IdeProgramRoot>/settings/agent-tools.json`
* 도구 호출 로그: `conversations/tool-calls.jsonl` + SQLite `agent_tool_calls` (DEC-050)
* DeepSeek 어댑터: `DeepSeekChatModelClient`
* CLI: `agent-run` 명령
* 채팅 통합: `ChatService`가 동일 프로토콜로 도구 호출, WPF는 도구 단계 라벨 표시

## 보안 기준 (DEC-046)

* 허용 스킴 http/https, 차단 file/ftp/data/javascript 등
* 차단 호스트/대역: localhost, 0.0.0.0, 루프백, 사설망, link-local, unique-local, 빈/과장 URL
* 응답 크기·문자 수·리다이렉트·타임아웃 제한
* 로그에는 전체 URL/시크릿을 남기지 않고 host 정도만 남긴다
* 도구 실패는 앱을 죽이지 않고 실패 ToolResult로 반환한다
* 테스트는 실제 외부 URL을 호출하지 않는다 (가짜 HTTP 핸들러 사용)

## 완료 기준

* 사용자 단일 Request에서 LLM과 도구가 다회차로 주고받아 최종 답변을 만든다.
* LLM은 URL을 직접 열지 않고 도구를 통해서만 외부에 접근한다.
* 도구 목록은 list_tools 디스커버리로 제공되고, 감독이 전역 allowlist로 제한할 수 있다.
* 도구는 읽기 전용이며, 상태/기준/산출물/파일을 직접 변경하지 않는다.
* CLI `agent-run`과 WPF 채팅 모두 Agent Loop를 사용한다.
* 빌드 경고 0/오류 0, 테스트 전체 통과.

## 후속 개선 (v0.5+)

Phase 8.5 완료 이후, 검색·도구 사용 안정화와 진단을 위해 다음을 반영했다. 세부는 Decision Log 참조.

* 진단 로깅: LLM 요청/응답 전체 `[Info]`, 도구 I/O 전체 `[Debug]`를 SystemLog에 기록. (DEC-057)

* 채팅 도구 호출을 `requests` 배열로 강제 + 병렬 실행 + 부분 실패 허용. (DEC-059)
* 모델 응답 JSON 추출을 "첫 균형 객체"로 견고화(여분 `}`/래퍼 태그/다중 객체 대응). (DEC-060)

# Phase 10. AI 글쓰기 도우미 UI

## 0. 설계 확정 (Final) — DEC-069 ~ DEC-078 반영

> 아래 §1~§9는 초기 탐색안이다. 토론으로 확정한 최종 설계는 본 §0이며, 충돌하는 부분은 §0을 우선한다.
> (관련 결정: [[DEC-069]] ~ [[DEC-072]], 구현/구조: [[DEC-073]] WPF 3모듈, [[DEC-074]] 본문 LLM 편집, [[DEC-075]] `<imported>` 격리, [[DEC-076]] 정책·프로바이더 공통화, [[DEC-077]] 메뉴 개편, [[DEC-078]] WorkspaceWindowBase)

### 0.1 최종 레이아웃 (3열)

```text
┌─────────┬───────────────────────────┬──────────────┐
│         │   목차      │     본문     │   대화 로그   │
│ 프로젝트 │────────────┴─────────────│              │
│  목록   │   아티팩트 (카드, 낮게)    │    입력창     │
└─────────┴───────────────────────────┴──────────────┘
  좌: 프로젝트   중앙(상: 목차|본문, 하: 아티팩트)   우: 대화 도킹
```

* 좌: 프로젝트 목록
* 중앙: 위 = 목차(트리) | 본문(편집기) 2분할, 아래 = 아티팩트(카드형, 높이 낮게)
* 우: 단일 대화 — 위 대화 로그, 아래 입력창 (상시 도킹)

### 0.2 대화 (우측 단일 도킹)

* 목차/본문 하단 임베드 대화 및 스코프별 대화는 **폐기**. 대화는 우측 단일 도킹창 하나.
* 입력: 우측 입력칸에서 Enter=전송, Shift+Enter=줄바꿈. **전역 Enter / 팝업 제거.**
* 사용자가 대화로 의도("본문 바꿔줘" 등)를 전달하면 LLM이 도구로 편집을 수행한다.

### 0.3 편집 대상 = 편집창 내용 (파일 아님)

* LLM은 파일이 아니라 **편집창(메모리) 내용**을 다룬다. 파일 직접 접근/쓰기는 계속 금지.
* 현재 내용은 상시 주입하지 않고 **온디맨드**로만 준다(토큰 절약): 본문 수정 요청 시 LLM이 `get_body`로 현재 본문을 받는다.
* 본문 수정은 자동 적용하지 않는다. LLM이 **수정 전문**을 제시하면 **[이전 | 수정] 비교 창**을 띄우고 **[변경]/[취소]**로 사용자가 확정한다.
* 목차 LLM 편집은 **보류**(설계 미확정).

### 0.4 저장 (편집창 → 프로젝트 루트 파일)

* 목차/본문 파일은 `.llmide`가 아니라 **프로젝트 폴더 직할**에 둔다(읽기 도구가 바로 접근). 파일명은 IDE가 정하되 목차 항목 id로 역추적 가능.
* 저장 트리거: ① LLM 편집 확정 직후 ② 사용자 `Ctrl+S` ③ 포커스 이동(예: 본문 편집 중 다른 목차 클릭).
* 메뉴: **프로젝트 > 저장** (`Ctrl+S`).

### 0.5 아티팩트

* 카드형 표시, 높이 낮게(목차/본문이 위쪽을 넓게 차지).
* 클릭 → 뷰어 열기 → 복제 유지.
* 본문 일부 선택 → 우클릭 → 아티팩트 추출 유지(기존 대화 추출과 동일 메커니즘).
* **드래그앤드롭(아티팩트↔본문 주입)은 취소.**

### 0.6 신규 도구 (편집창 대상, 파일 금지 유지) — 구현됨 ([[DEC-074]])

* `get_body`: 현재(또는 지정) 섹션 본문을 온디맨드로 주입.
* `propose_body_edit`: LLM이 수정 전문을 제안 → `IDocumentBodyBridge`(Core)가 UI 스레드로 마샬링 → `[이전 | 수정]` 비교 창(BodyDiffDialog) → `[변경]/[취소]` 확정(§0.3). 자동 적용 안 함.
* 본문 도구는 `IDocumentBodyBridge` 주입 시에만 등록(Writer 전용).
* 목차 편집 도구: 보류.

### 0.7 진행 상황 정리

* 폐기: Enter→팝업 대화창, 목차/본문 하단 임베드 대화, 스코프별 대화 로그, 아티팩트 D&D 주입, **본문 요약 hover 팝업(§4.6)**.
* 구현 완료:
  * 목차 추가/하위/이름변경/삭제, 더블클릭 인라인 편집, 본문 파일 연동·저장(outline.json + `<id>.md`), 목차 D&D 재정렬(시각효과 다듬기만 후속).
  * 본문 LLM 편집: `get_body`/`propose_body_edit` + 승인창([[DEC-074]]).
  * WPF 3모듈 분리(Lib/Chat/Writer)와 공유 핸들러 베이스([[DEC-073]], [[DEC-078]]).
  * 정책·프로바이더 설정 앱 루트 공통화 + 메뉴 개편(편집>LLM 추가, 룰 편집 제거)([[DEC-076]], [[DEC-077]]).
  * 외부 가져온 대화 `<imported>` 격리([[DEC-075]]).
* 보류: 목차 LLM 편집.

### 0.8 이미지 아티팩트 · 본문 이미지 삽입 · 미리보기 (계획) — [[DEC-080]], [[DEC-081]]

이미지를 아티팩트로 다루고, 본문에는 참조 태그만 넣고, 미리보기에서 렌더해 본다. LLM은 이미지를 읽지 않는다(순수 UI/문서 기능). 이미지 LLM 생성은 후속.

구현 순서:

1. **바이너리 이미지 아티팩트 지원**([[DEC-080]]) — 아티팩트 영역에 이미지 파일 드래그 → `.llmide/artifacts/<id>.png`로 바이트 저장, `type=image`, 인덱스에 등록. `read_artifact`는 이미지에 본문 대신 메타데이터만 반환(텍스트로 바이너리 토하지 않음).
2. **이미지 카드 + 클릭 뷰어**([[DEC-080]]) — 아티팩트 카드에 이미지 표시(썸네일/아이콘), 클릭 시 ArtifactViewer의 image 분기로 원본 보기. 뷰어 비율 조절(Stretch/줌)은 후속.
3. **본문 D&D 이미지 참조 삽입**([[DEC-081]]) — 아티팩트를 본문 편집기로 드래그 → 드롭 지점(`GetCharacterIndexFromPoint`)에 마크다운 이미지 참조 삽입. 바이너리/내용 주입이 아니라 **참조 태그만**. 태그 포맷은 후속 폭(width) 힌트 확장 여지를 남긴다(`![제목](.llmide/artifacts/<id>.png)`).
4. **본문 미리보기 패널/버튼**([[DEC-081]]) — 본문 영역 우측 끝에 미리보기 버튼. 누르면 본문 마크다운을 Markdig.Wpf(MarkdownText)로 텍스트+이미지 렌더해 보여준다. 상대→절대 `file://` 경로 글루 필요.

## 2. 전체 레이아웃

메인 윈도우 본문은 4분할 구조로 구성한다.

```text
┌────────────┬──────────────┬──────────────────────┬──────────────┐
│ 프로젝트   │ 목차          │ 본문                  │ 아티팩트      │
│ 목록       │ 편집창        │ 편집창                │ 목록창        │
└────────────┴──────────────┴──────────────────────┴──────────────┘
```

각 영역의 역할은 다음과 같다.

```text
프로젝트 창
- 프로젝트 목록
- 프로젝트 생성 / 이름 변경 / 복제 / 삭제
- 프로젝트 선택

목차 편집창
- 현재 글쓰기 문서의 목차 Tree
- 목차 추가 / 삭제 / 이름 변경 / 이동
- 목차용 AI 대화 로그
- 목차용 AI 입력창

본문 편집창
- 선택된 목차 아이템에 연결된 본문 편집기
- Markdown 또는 일반 텍스트 편집
- 본문용 AI 대화 로그
- 본문용 AI 입력창

아티팩트 목록창
- 저장된 아티팩트 목록
- 아티팩트 조회 / 삭제 / 복사
- 아티팩트를 본문으로 드래그 삽입
```

## 4.1 구조

```text
┌─────────────────────┐
```

## 4.2 목차 Tree

목차 아이템은 Tree 구조로 관리한다.

```text
1. 서론
  1.1 문제의식
  1.2 글의 목적
2. LLM의 구조
  2.1 Stateless LLM
  2.2 Context Window
3. LLM IDE의 필요성
```

목차 아이템은 다음 정보를 가진다.

```json
{
  "section_id": "sec_001",
  "title": "서론",
  "level": 1,
  "order": 1,
  "number": "1",
  "body_path": "sections/sec_001.md",
  "summary": "",
  "status": "drafting",
  "include_in_export": true,
  "children": []
}
```

```text
추가
삭제
이름 변경
드래그 & 드랍 이동
상위/하위 구조 변경
자동 장절번호 재계산
본문 요약 팝업
본문 편집창 연결
```

## 4.4 드래그 & 드랍

목차 아이템은 드래그 & 드랍으로 위치를 바꿀 수 있다.

지원 이동:

```text
같은 레벨 내 순서 이동
다른 부모 아래로 이동
상위 섹션으로 이동
하위 섹션으로 이동
```

이동 후 처리:

```text
1. 기존 부모에서 노드 제거
2. 대상 위치에 노드 삽입
3. 전체 Tree 순서 재계산
4. level 재계산
5. 장절번호 자동 재생성
6. outline 저장
7. 화면 갱신
```

금지:

```text
자기 자신 아래로 이동 금지
자기 자신의 하위 노드 아래로 이동 금지
순환 Tree 생성 금지
```

## 4.5 장절번호 자동 정렬

목차에 표시되는 장절번호는 저장된 고정 문자열이 아니라, Tree 구조를 기준으로 자동 계산한다.

예:

```text
1
1.1
1.2
2
2.1
2.1.1
```

드래그 & 드랍으로 목차 위치가 바뀌면 번호는 자동으로 다시 계산된다.

번호 계산 규칙:

```text
root 첫 번째 항목 = 1
root 두 번째 항목 = 2
첫 번째 항목의 첫 번째 자식 = 1.1
첫 번째 항목의 두 번째 자식 = 1.2
두 번째 항목의 첫 번째 자식 = 2.1
```

본문 Export 시에도 이 정렬된 번호와 순서를 사용한다.

## 4.6 본문 요약 팝업

```text
상태
```


요약 생성 방식은 후속 단계에서 AI 요약 또는 수동 요약으로 확장할 수 있다.

목차 아이템을 클릭하면 해당 아이템과 연결된 본문 파일을 본문 편집창에 연다.

```text
3. body_path 파일이 있으면 자동 로드
4. 파일이 없으면 빈 본문으로 시작

```

## 5. 본문 편집창

## 5.1 구조

본문 편집창은 위에서부터 다음 순서로 구성한다.

```text
┌──────────────────────────────┐

│ - 드래그 선택 가능             │
│ - 복사 가능                    │

├──────────────────────────────┤

└──────────────────────────────┘
```

## 5.2 본문 편집기

본문 편집기는 선택된 목차 아이템에 연결된 본문을 표시한다.

기능:

```text
본문 작성
본문 수정
본문 일부 선택
본문 일부 삭제
본문 일부 복사
본문 일부를 아티팩트로 추출
아티팩트 삽입
자동 저장 또는 명시 저장
```

본문 파일이 존재하면 자동으로 로드한다.
본문 파일이 없으면 빈 편집기를 표시한다.

## 5.3 본문 저장

본문 내용은 목차 아이템별 파일로 저장한다.

예시 저장 구조:

```text
<ProjectRoot>/
 └─ writing/
     └─ documents/
         └─ doc_001/
             ├─ document.json
             ├─ outline.json
             ├─ sections/
             │   ├─ sec_001.md
             │   ├─ sec_002.md
             │   └─ sec_003.md
             └─ exports/
                 └─ draft.md
```

본문 편집창은 현재 선택된 `section_id`의 `body_path`를 기준으로 파일을 읽고 쓴다.

---

## 5.4 본문 일부를 아티팩트로 추출

본문 편집창에서 작성한 글 일부를 드래그로 선택하고 우클릭하면 `아티팩트로 추출`할 수 있다.

동작:

```text
1. 사용자가 본문 일부 선택
2. 우클릭
3. 아티팩트로 추출 선택
4. Artifact 제목 / 유형 입력
5. 선택 영역을 Artifact로 저장
6. 저장된 Artifact를 아티팩트 목록창에 표시
```

이 기능은 기존 대화 응답에서 선택 영역을 아티팩트로 추출하던 기능과 동일한 사용자 경험을 유지한다.

## 5.5 아티팩트 삽입

아티팩트 목록창에서 아티팩트를 본문 편집창으로 드래그하면, 현재 커서 위치 또는 드롭 위치에 아티팩트 내용을 삽입한다.

동작:

```text
1. 사용자가 아티팩트 목록에서 항목을 드래그
2. 본문 편집창 위에 드롭
3. read_artifact 또는 ArtifactService로 내용 조회
4. 본문 편집창의 드롭 위치에 내용 삽입
5. 본문 수정 상태로 표시
6. 저장 시 섹션 본문 파일에 반영
```

삽입 옵션은 후속으로 확장할 수 있다.

```text
원문 그대로 삽입
인용 블록으로 삽입
링크/참조 형태로 삽입
요약 후 삽입
```

초기 구현은 “원문 그대로 삽입”을 기본으로 한다.

## 6. 목차 AI 대화창

## 6.1 위치

목차 AI 대화창은 목차 편집창 하단에 상시 표시한다.

구조:

```text
목차 Tree
→ 목차 AI 대화로그
→ 목차 AI 입력창
```

---

## 6.2 역할

목차 AI 대화창은 문서 구조와 목차에만 적용한다.

목차 AI에게 전달할 수 있는 작업:

```text
목차 초안 만들어줘
현재 목차 구조를 개선해줘
이 목차를 논문 구조로 바꿔줘
이 섹션을 두 개로 나눠줘
빠진 장을 제안해줘
목차 순서를 검토해줘
서론 아래에 들어갈 하위 절을 제안해줘
```

목차 AI는 본문 내용을 직접 수정하지 않는다.
목차 변경도 즉시 적용하지 않고, 제안 또는 사용자 승인 기반 적용으로 처리한다.

---

## 6.3 목차 AI 맥락

목차 AI 요청에는 다음 맥락을 우선 포함한다.

```text
Project State
현재 문서 정보
현재 outline tree
선택된 목차 아이템
관련 Artifact 목록
필요 시 Rolling Context Summary
사용자 입력
```

본문 전체는 기본적으로 포함하지 않는다.
필요한 경우 선택된 섹션 요약 또는 사용자가 명시한 섹션만 포함한다.

## 7. 본문 AI 대화창

## 7.1 위치

본문 AI 대화창은 본문 편집창 하단에 상시 표시한다.

구조:

```text
본문 편집기
→ 본문 AI 대화로그
→ 본문 AI 입력창
```

---

## 7.2 역할

본문 AI 대화창은 현재 선택된 본문 섹션에 적용한다.

본문 AI에게 전달할 수 있는 작업:

```text
이 문단 이어서 써줘
이 문장을 더 자연스럽게 바꿔줘
이 섹션의 논리를 검토해줘
이 섹션을 논문체로 바꿔줘
이 섹션을 블로그체로 바꿔줘
근거가 부족한 부분을 찾아줘
이 섹션의 요약을 만들어줘
이 섹션에 들어갈 참고자료를 찾아줘
```

본문 AI는 AI 웹세션처럼 현재 본문을 참고해 응답한다.
다만 본문 파일을 자동으로 저장하거나 덮어쓰지는 않는다.

---

## 7.3 본문 AI 수정 방식

본문 AI는 다음 방식으로 동작한다.

초기 원칙:

```text
AI는 수정안을 제안한다.
사용자가 본문에 반영한다.
```

후속 확장:

```text
선택 영역 바꾸기
현재 커서 위치에 삽입
섹션 끝에 추가
before/after diff 적용
```

파일 자동 수정은 하지 않는다.

# Phase 11. Writing Project State / Plan

## 목표

Project State를 기능 시험 기록이 아니라 **글쓰기 프로젝트의 작업 지휘판**으로 재정의한다.

Project State는 토큰 사용량, Context Package 크기, Compression 상태 같은 런타임 진단 정보가 아니다.
Project State는 사용자가 승인한 글쓰기 목표, 현재 단계, 현재 섹션, 할 일, 결정 사항을 관리한다.

## Project State 필드 후보

```json
{
  "project_goal": "",
  "writing_goal": "",
  "document_type": "",
  "target_audience": "",
  "current_stage": "",
  "current_section": "",
  "current_task": "",
  "completed_items": [],
  "in_progress_items": [],
  "next_actions": [],
  "blockers": [],
  "last_decision": "",
  "updated_at": ""
}
```

## 필드 의미

```text
project_goal
- 프로젝트 전체 목표

writing_goal
- 작성하려는 글의 목표

document_type
- article, paper, thesis, blog, README, report 등

target_audience
- 대상 독자

current_stage
- research, outline, drafting, revision, finalizing 등

current_section
- 현재 작업 중인 장/절/문단

current_task
- 지금 수행 중인 구체 작업

completed_items
- 완료한 작업

in_progress_items
- 진행 중인 작업

next_actions
- 다음 할 일

blockers
- 막힌 점

last_decision
- 마지막 확정 결정
```

## 구현 항목

* `project-state.json` 스키마 확장
* 기존 Project State와 하위 호환
* WPF Project State / Plan Editor 추가
* Project Goal 입력
* Writing Goal 입력
* Document Type 입력 또는 선택
* Target Audience 입력
* Current Stage 입력 또는 선택
* Current Section 입력
* Current Task 입력
* Completed / In Progress / Next Actions / Blockers 편집
* Last Decision 편집
* Chat 요청에 Project State를 글쓰기 맥락으로 주입

## 완료 기준

* 사용자가 글쓰기 목표와 현재 작업 단계를 명시적으로 저장할 수 있다.
* AI가 응답할 때 현재 글쓰기 목표, 독자, 문서 유형, 현재 섹션을 참고할 수 있다.
* 기능 테스트 기록과 글쓰기 프로젝트 상태가 섞이지 않는다.
* Project State는 사용자가 직접 편집하고 승인한 상태로 유지된다.

## 상태

# Phase 12. Research / Source Workflow

## 목표

AI가 글쓰기와 논문 작성에 필요한 자료를 조사하고, 프로젝트 내부 자료와 외부 웹 자료를 읽어 요약할 수 있게 한다.

```text
사용자 요청
→ artifacts_list
→ read_artifact
```

* 웹 검색 결과에서 중요한 URL을 다시 fetch하도록 유도
* 조사 결과의 출처 URL을 응답에 보존
* WPF에서 도구 호출 상태와 결과 요약 표시 개선
* 도구 호출 로그 조회 보강

```text
SourceNote
LiteratureNote
ReferenceSummary

QuoteCandidate
```

# Phase 14. Writing Review / Revision Workflow

## 목표

AI가 초안의 논리, 구조, 표현, 일관성, 누락 지점을 검토하고 수정안을 제안할 수 있게 한다.

이 단계에서도 AI는 파일을 직접 수정하지 않는다.
AI는 리뷰와 수정안을 제안하고, 사용자가 선택해 Artifact 또는 파일로 저장한다.

## 리뷰 유형

```text
Structure Review
- 글의 전체 구조 점검

Logic Review
- 주장, 근거, 결론의 연결성 점검

Clarity Review
- 문장 명확성 점검

Style Review
- 문체, 톤, 독자 적합성 점검

Citation Review
- 참고자료 사용 여부와 출처 누락 점검

Gap Review
- 빠진 논점, 보강할 부분 제안

Revision Proposal
- 수정안 제안
```

## 구현 항목

* Review용 프롬프트 정리
* 선택한 Artifact 리뷰
* 선택한 파일 리뷰
* 현재 Project State 기준 리뷰
* Criteria 기준 리뷰
* 리뷰 결과 Artifact 저장
* 수정안 Artifact 저장
* Before / After 형식 출력
* 수정 이유와 수정문 분리
* WPF에서 리뷰 결과 보기 개선

## 완료 기준

* 사용자는 초안 Artifact를 AI에게 리뷰시킬 수 있다.
* 사용자는 프로젝트 파일을 AI에게 리뷰시킬 수 있다.
* AI는 수정안을 직접 파일에 적용하지 않고 제안한다.
* 사용자는 리뷰 결과와 수정안을 Artifact로 저장할 수 있다.
* 글쓰기 목표, 대상 독자, 문서 유형이 리뷰 기준으로 사용된다.

# Phase 15. Writing File Workflow

## 목표

프로젝트 폴더 안의 원고, 메모, 참고자료 파일을 글쓰기 맥락으로 활용한다.

기존 `read_file`, `list_files` 도구는 이미 프로젝트 폴더 내부 파일 읽기를 지원한다.
이 단계에서는 이를 글쓰기 작업 흐름에 맞게 정리하고, 명시적 파일 내보내기 기능을 추가한다.

## 원칙

* AI는 프로젝트 파일을 읽을 수 있다.
* AI는 파일을 직접 수정하지 않는다.
* 파일 쓰기는 사용자가 명시적으로 실행한 내보내기 기능으로만 수행한다.
* `.llmide` 내부 파일은 raw file 도구로 읽지 않는다.
* ArtifactService를 통한 Artifact 조회는 허용한다.

## 구현 항목

* 프로젝트 파일 목록 패널 개선
* 원고 / 메모 / 자료 파일 구분 표시
* 파일 읽기 요청 UX 정리
* 파일 기반 요약 요청 UX 정리
* Artifact를 Markdown 파일로 내보내기
* FinalDraft Artifact를 파일로 저장
* 파일 저장 전 확인 다이얼로그
* 동일 파일 존재 시 덮어쓰기 확인
* 저장 이력 기록

## 완료 기준

* 사용자는 프로젝트 폴더 파일 목록을 확인할 수 있다.
* AI는 사용자가 요청한 프로젝트 파일을 읽고 요약할 수 있다.
* 사용자는 Artifact를 명시적으로 파일로 내보낼 수 있다.
* AI가 사용자 승인 없이 파일을 수정하지 않는다.
* 파일 내보내기는 추적 가능하게 기록된다.

```text
대기
```

## 7. MVP 완료 기준 (충족)

MVP(Phase 1~9)는 다음 조건을 모두 충족했다.

* 긴 대화에서도 과거 전체 원문을 매 요청에 포함하지 않는다.
* 과거 맥락은 롤링 맥락 요약로 전달한다.
* 최근 대화는 최근 대화 창(장기 대화 user 5턴)로 전달한다.
* 롤링 맥락 요약는 LLM Provider API를 통해 생성한다.
* 원본 대화 로그와 압축 맥락은 별도로 보존한다.
* Compression 실패 시 원본 대화과 사용자 응답은 유지한다.
* 각 요청에서 어떤 압축 맥락이 사용되었는지 추적할 수 있다.
* `요약 + 창`를 기본 맥락 관리 전략으로 사용한다.
* 프로젝트 상태와 Criteria를 저장하고 요청에 포함할 수 있다.
* 산출물를 저장하고 요청에 첨부할 수 있다.
* 읽기 전용 Agent Loop와 도구(web_search, fetch_url, read_file, list_files, artifacts_list, read_artifact)로 단일 Request에서 자료 조사·읽기를 수행한다.
* CLI와 WPF가 동일한 Core와 `.llmide` 데이터를 사용한다.
* WPF에서 현재 Core/CLI 기반 기능을 사용할 수 있다.

MVP는 종료되었다. 이후는 Phase 10+ AI 글쓰기 작업실 제품화로 진행한다.
기존 후속 개념(Context Notes / File Store / State Update Candidate)은 글쓰기 작업실의 Project State·파일/연구 워크플로·State Candidate로 재정의했고, Local Server는 Phase 17로 둔다. (DEC-067, DEC-068)
