# LLM IDE Architecture Baseline v0.1

## 1. 목적

이 문서는 LLM IDE의 현재 아키텍처 기준선을 정의한다.

Architecture Baseline은 다음을 고정한다.

* 프로젝트 저장 구조
* 애플리케이션 계층 구조
* 데이터 저장 방식
* 요청 실행 흐름
* 맥락 관리 구조
* Provider 분리 구조
* CLI / WPF / Server 관계
* 추적성과 실패 처리 기준

이 문서는 개발 로드맵이 아니라, 구현이 따라야 하는 구조 기준이다.

---

## 4. 계층 책임

### 4.1 LlmIde.Core

비즈니스 로직 계층이다.

포함 책임:

* Project 관리
* Project Registry 관리
* Criteria 관리
* Project State 관리
* Context Builder
* Rolling Context 관리
* Artifact 관리
* State Candidate 관리
* Provider 추상화
* 요청 실행 흐름 정의

Core는 특정 UI, 파일 시스템 세부 구현, 특정 Provider 구현체에 종속되지 않는다.

---

### 4.2 LlmIde.Infrastructure

외부 시스템 연동 계층이다.

포함 책임:

* 파일 저장소 구현
* JSON 저장
* JSONL 저장
* SQLite 저장소 구현
* Provider 구현체
* Credential 저장소
* 파일 추출기
* 로컬 경로 처리

Infrastructure는 Core가 정의한 인터페이스를 구현한다.

---

### 4.3 LlmIde.Cli

MVP 실행 환경이다.

포함 책임:

* 프로젝트 초기화
* 프로젝트 열기
* 프로젝트 목록 관리
* 대화 실행
* Criteria 관리
* Project State 관리
* Rolling Context Compression 실행
* Artifact 관리

CLI는 Core를 호출하는 어댑터다.
비즈니스 로직을 CLI에 두지 않는다.

---

### 4.4 LlmIde.Wpf

후속 GUI 계층이다.

원칙:

```text
WPF는 Core를 호출하는 UI 계층이다.
비즈니스 로직은 Core에만 존재한다.
```

포함 예정 기능:

* Project Explorer
* Project Registry
* Conversation View
* Criteria Editor
* Project State Editor
* Artifact Manager
* Context Manager
* Provider Settings

---

### 4.5 LlmIde.Server

후속 로컬 서버 계층이다.

목표:

```text
CLI와 WPF 외부에서도 LLM IDE 기능을 호출할 수 있게 한다.
```

포함 예정 기능:

* 로컬 TCP 서버
* 로컬 UDP 서버
* 로컬 HTTP API 검토
* Project 관리 API
* Provider 모델 조회 API
* Chat 요청 API
* Streaming Chat 응답 API
* Criteria 관리 API
* Artifact 관리 API

원칙:

```text
Server는 Core를 호출하는 어댑터 계층이다.
비즈니스 로직은 Core에만 존재한다.
```

## 5. Project Registry 구조

Project는 이름 기반으로 관리한다.

프로젝트 이름은 다음 기능의 기본 키다.

* 프로젝트 목록
* 프로젝트 열기
* 프로젝트 제거
* 프로젝트 삭제
* 프로젝트 선택

Project Registry는 IDE 실행 프로그램 하부의 고정 폴더에 둔다.

```text
<IdeProgramRoot>/
 ├─ llmide
 ├─ LlmIde.Core.dll
 ├─ LlmIde.Infrastructure.dll
 ├─ project/
 │   └─ projects.json
 └─ <ProjectName>/
```

`<IdeProgramRoot>/project` 위치는 항상 고정이다.
이 폴더는 프로젝트 정보만 저장한다.
실제 프로젝트 데이터는 저장하지 않는다.

`projects.json` 형식:

```json
{
  "projects": [
    {
      "name": "DefaultProject",
      "path": "<ProjectRoot>",
      "created_at": ""
    }
  ]
}
```

프로젝트 이름과 경로는 수정 가능해야 한다.

## 12. Request 실행 흐름

기본 Chat Request 흐름:

```text
User Input
 → Context Builder
 → Context Package 생성
 → Provider API Request
 → Assistant Response
 → Raw Conversation Log 저장
 → Request Log 저장
 → Compression Request 실행
 → Rolling Context Summary 갱신
```

Compression Request는 사용자 응답 이후 별도의 내부 LLM 요청으로 실행한다.

Compression Request 실패는 Chat Request 실패가 아니다.

## 13. Context Package 구조

Context Package는 특정 API 요청에 실제로 들어간 맥락 스냅샷이다.

기본 구조:

```json
{
  "request_id": "req_001",
  "system_rule": "",
  "active_criteria": [],
  "project_state": {},
  "rolling_context_summary": "",
  "context_notes": [],
  "attached_messages": [],
  "attached_artifacts": [],
  "attached_files": [],
  "recent_turns": [],
  "user_request": ""
}
```

Context Package는 다음을 보장한다.

* 요청 재현성
* 응답 추적성
* 포함 맥락 검증
* 감리 가능성
* 디버깅 가능성

## 14. API 요청 맥락 조립 구조

Chat Request에 포함되는 맥락 구조는 다음이다.

```text
[System Rule]
[Active Criteria]
[Project State]
[Rolling Context Summary]
[Recent Window]
[Manual Attachments]
[Artifacts]
[User Request]
```

규칙:

* 과거 전체 대화 원문은 포함하지 않는다.
* 과거 대화는 Rolling Context Summary로 표현한다.
* 최근 대화만 제한된 개수의 원문으로 포함한다.
* 현재 사용자 요청은 항상 원문으로 포함한다.
* Manual Attachments는 사용자가 명시적으로 선택한 경우에만 포함한다.

우선순위:

```text
1. System Rule
2. Active Criteria
3. Project State
4. User Request
5. Manual Attachments
6. Artifacts
7. Rolling Context Summary
8. Recent Window
```

## 15. Context Management Architecture

LLM IDE의 기본 맥락 관리 구조는 다음이다.

```text
Raw Conversation Log
 + Rolling Context Summary
 + Recent Window
```

### 15.1 Raw Conversation Log

모든 user / assistant 원문 대화를 저장한다.

용도:

* 감사
* 재현
* 검색
* 디버깅
* 추적

Raw Conversation Log는 장기 기록의 원본이다.
하지만 매 API 요청에 전체 원문을 포함하지 않는다.

---

### 15.2 Rolling Context Summary

과거 대화 맥락을 압축한 요청 주입용 요약이다.

특징:

* LLM Provider API로 생성한다.
* 원본 대화 로그를 대체하지 않는다.
* 다음 chat 요청에 과거 맥락으로 포함한다.
* 실패 시 기존 Summary를 유지한다.

저장 위치:

```text
.llmide/conversations/rolling-context/current.md
.llmide/conversations/rolling-context/history/
.llmide/conversations/rolling-context/index.jsonl
```

---

### 15.3 Recent Window

최근 N개의 user / assistant 발화를 원문으로 포함하는 제한된 대화 창이다.

역할:

* 직전 흐름 유지
* 지시어 참조 유지
* 말투와 형식 유지
* 짧은 문맥 연속성 보장

MVP에서는 Recent Window를 `0`으로 기록할 수 있다.
이후 설정값에 따라 확장한다.

## 16. Rolling Context 저장소

구조:

```text
rolling-context/
 ├─ current.md
 ├─ history/
 │   └─ rctx_000001.md
 └─ index.jsonl
```

### 16.1 current.md

최신 Rolling Context Summary다.
다음 chat 요청에 과거 맥락으로 포함된다.

---

### 16.2 history/

과거 Rolling Context Summary 버전을 보존한다.

새 Summary가 생성되면 history에 저장한다.
이전 Summary는 삭제하지 않는다.

---

### 16.3 index.jsonl

Rolling Context Summary 생성 이력을 저장한다.

레코드 형식:

```json
{
  "rolling_context_id": "rctx_000001",
  "source_request_id": "req_000001",
  "previous_rolling_context_id": null,
  "content_path": "conversations/rolling-context/history/rctx_000001.md",
  "is_current": true,
  "created_at": "",
  "provider": "deepseek",
  "model": "deepseek-chat",
  "status": "completed",
  "error": null
}
```

허용 `status`:

```text
completed
failed
superseded
```

## 17. Compression Request 구조

Compression Request는 사용자 응답 생성 이후 실행하는 내부 LLM 요청이다.

입력 구조:

```text
[Compression Rule]

[Previous Rolling Context Summary]
기존 current.md 내용

[Current User Message]
이번 user 원문

[Current Assistant Response]
이번 assistant 원문

[Task]
위 내용을 병합하여 다음 요청에 사용할 Rolling Context Summary를 갱신하라.
```

규칙:

* 과거 전체 원문 대화를 포함하지 않는다.
* 이전 Summary와 현재 user / assistant 대화만 포함한다.
* 사용자에게 직접 출력하지 않는다.
* 결과는 rolling-context 아래에 저장한다.
* 실패해도 Chat Request를 실패로 처리하지 않는다.

---

## 18. Compression 실패 처리

Compression 실패 시 처리 기준:

```text
사용자 응답 성공
Raw Conversation Log 저장 성공
Compression Request 실패
```

결과:

* 사용자 응답은 유지한다.
* Raw user / assistant message는 유지한다.
* 기존 current.md는 유지한다.
* requests.jsonl에 compression_failed를 기록한다.
* 다음 chat은 이전 Summary를 사용한다.

금지:

* Compression 실패 때문에 사용자 응답을 폐기하지 않는다.
* Raw Conversation Log를 롤백하지 않는다.
* 빈 Summary로 current.md를 덮어쓰지 않는다.

```text
 ├─ compression-rule.md
```

---

### 19.2 compression-rule.md

Rolling Context Summary 생성을 위한 압축 전용 규칙이다.

---

### 19.3 context-policy.json

Context Builder와 Compression 동작 정책이다.

기본 구조:

```json
{
  "context_management_strategy": "summary_plus_window",
  "include_rolling_context_summary": true,

  "recent_turn_count": 0,
  "max_recent_turn_chars": 0,
  "max_rolling_context_chars": 24000,

  "compression_provider": "deepseek",
  "compression_model": "deepseek-chat",
  "compression_after_chat": true,
  "compression_failure_strategy": "keep_previous",
  "rag_enabled": false
}
```

허용 `context_management_strategy`:

```text
window_only
summary_only
summary_plus_window
rag
```

MVP 기본값:

```text
summary_plus_window
```

허용 `compression_failure_strategy`:

```text
keep_previous
clear_current
fail_chat
```

MVP 기본값:

```text
keep_previous
```

## 20. Provider Architecture

Core는 특정 LLM Provider에 종속되지 않는다.

구조:

```text
LlmIde.Core
 └─ Provider Interface

LlmIde.Infrastructure
 ├─ DeepSeek Provider
 ├─ OpenAI Provider 후보
 └─ Gemini Provider 후보
```

MVP 첫 Provider는 DeepSeek이다.

Provider 관련 요구사항:

* Provider 인터페이스 정의
* DeepSeek Provider 구현
* API Key 관리
* 모델 목록 조회
* 기본 모델 교체
* Streaming 응답 처리
* Markdown 원문 출력 보존

API Key는 프로젝트 문서에 평문 저장하지 않는 것을 원칙으로 한다.

## 21. Artifact Architecture

Artifact는 중요한 AI 응답 또는 사용자가 보존하려는 산출물이다.

저장 구조:

```text
artifacts/
 ├─ artifacts.index.json
 └─ <artifact_id>.md
```

Artifact 원칙:

* 원본 chat 응답은 그대로 Conversation Log에 남긴다.
* Artifact는 원본 응답에서 분리된 재사용 가능한 산출물이다.
* AI는 Artifact 후보를 제안할 수 있다.
* 사용자 승인 없이 Artifact를 확정 저장하지 않는다.
* 태그가 붙은 영역만 Artifact 후보로 추출한다.
* C# 코드는 자연어 의미를 임의 추측해 Artifact를 분류하지 않는다.

## 22. File Store Architecture

File Store는 프로젝트 파일을 AI 맥락으로 활용하기 위한 구조다.

저장 구조:

```text
files/
 ├─ files.index.json
 ├─ extracted/
 │   └─ <file_id>.txt
 └─ summaries/
     └─ <file_id>.md
```

MVP 범위:

* 파일 등록
* 텍스트 추출
* 파일 요약
* 명시적 첨부

MVP 제외:

* Vector DB
* Embedding index
* Semantic retrieval
* Session/project RAG
* Query-based file context selection

RAG는 File Store 안정화 이후 후속 검토한다.

## 23. State Candidate Architecture

State Candidate는 AI가 제안한 상태 변경 후보를 관리한다.

저장 구조:

```text
state-candidates/
 └─ candidates.jsonl
```

원칙:

* AI는 상태 변경 후보를 제안할 수 있다.
* 사용자 승인 없이 Project State나 Criteria를 변경할 수 없다.
* 승인된 후보만 실제 상태에 반영한다.

## 24. Agent Boundary Architecture

LLM IDE는 에이전트 기능을 수용할 수 있는 구조로 설계한다.

그러나 MVP에서는 자율 실행 에이전트를 구현하지 않는다.

AI가 할 수 있는 것:

* 응답 생성
* 요약
* 상태 변경 후보 제안
* 산출물 초안 생성
* 파일/맥락 기반 분석

AI가 사용자 승인 없이 할 수 없는 것:

* Project State 변경
* Criteria 변경
* Artifact 확정 저장
* 파일 수정
* 프로젝트 삭제
* 외부 명령 실행
* 다음 작업 자동 실행

## 27. 초기화 실패 처리

프로젝트 폴더를 생성한 뒤 오류가 발생한 경우, 생성된 프로젝트 폴더 안에 초기화 진행 단계를 기록한다.

기록 파일:

```text
.llmide/init-progress.json
```

권한 오류가 발생하면 오류를 표시하고 즉시 중단한다.

중복 `DefaultProject` 오류 상황에서는 파일 저장과 폴더 생성을 금지한다.

## 28. 삭제 안전성

프로젝트 삭제는 두 단계로 구분한다.

```text
remove
= Project Registry 목록에서만 제거
= 실제 프로젝트 폴더 삭제하지 않음

delete
= 실제 프로젝트 폴더 삭제
= Project Registry 목록에서도 제거
```

`delete`는 다음 조건 없이는 실행하지 않는다.

```text
--confirm <project-name>
```

프로젝트에 API Key가 있으면 추가 확인이 필요하다.

```text
--confirm-api-key-delete
```

## 30. Architecture Summary

현재 Architecture Baseline은 다음으로 요약된다.

```text
Project Registry
→ Project Root
→ .llmide Metadata
→ Conversation DB
→ Raw Conversation Log
→ Rolling Context Summary
→ Context Builder
→ Context Package
→ Provider API Request
→ Response
→ Request Log
→ Compression Request
→ Updated Rolling Context Summary
```

한 줄 정의:

```text
LLM IDE Architecture는 stateless LLM Provider 위에 Project Runtime, Context Builder, Traceable Request Log를 얹은 구조다.
```
