# LLM IDE Product Principles v0.1

## 1. 제품 정체성

LLM IDE는 단순 채팅 앱이 아니다.

LLM IDE는 다음 역할을 한다.

```text
프로젝트 상태 관리 IDE
+ 장기 맥락 관리 런타임
+ 사용자 승인 기반 에이전트 도구 기반
```

LLM IDE는 AI가 모든 것을 기억하게 만드는 도구가 아니다.

```text
IDE가 프로젝트를 기억한다.
AI는 매 요청마다 IDE가 주입한 맥락을 기반으로 실행된다.
```

---

## 2. 핵심 원칙

```text
원본은 저장한다.
과거는 압축해서 넣는다.
최근은 원문으로 유지한다.
압축은 LLM에게 맡긴다.
```

LLM IDE는 모든 대화와 산출물을 보존하지만, API 요청에는 필요한 맥락만 선별하여 주입한다.

---

## 3. Stateless LLM, Stateful Product

LLM Provider 호출은 요청 단위로 독립 실행된다.

장기성은 LLM 내부가 아니라 LLM IDE의 Project Runtime이 제공한다.

```text
LLM은 계산 엔진이다.
기억은 애플리케이션이 만든다.
```

따라서 LLM IDE는 다음을 책임진다.

* 프로젝트 상태 저장
* 기준 저장
* 대화 로그 저장
* 맥락 압축
* 산출물 저장
* 파일 인덱스 관리
* 요청별 Context Package 생성
* 요청/응답 추적

---

## 4. Project 중심 원칙

Project는 LLM IDE의 최상위 작업 단위다.

Project는 이름 기반으로 관리한다.

```text
Project Name
→ Project Registry
→ Project Root
→ .llmide Metadata
```

프로젝트 이름은 다음 기능의 기본 키다.

* 프로젝트 목록
* 프로젝트 열기
* 프로젝트 제거
* 프로젝트 삭제
* 프로젝트 선택

실제 프로젝트 데이터는 Project Root 아래 `.llmide`에 저장한다.

---

## 5. Session 제거 원칙

LLM IDE는 Session 개념을 사용하지 않는다.

API 기반 구조에서는 장기 세션을 유지하지 않는다.

대신 다음 구조를 사용한다.

```text
Project
→ Conversation Log
→ Request
→ Context Package
```

Conversation Log는 Project에 직접 귀속된다.
API 호출의 실행 단위는 Request다.

---

## 6. Handoff 제거 원칙

LLM IDE는 Handoff 기능을 사용하지 않는다.

프로젝트 상태와 맥락은 이미 Project Runtime 안에 저장된다.
따라서 별도 handoff prompt를 만들어 세션 간 전달할 필요가 없다.

요청 재현성과 맥락 전달은 Context Package가 담당한다.

---

## 7. Context Package 원칙

Context Package는 특정 API 요청에 실제로 주입된 맥락 스냅샷이다.

Context Package는 다음을 보장한다.

* 요청 재현성
* 응답 추적성
* 포함 맥락 검증
* 디버깅 가능성
* 감리 가능성

LLM IDE는 “모델이 무엇을 봤는가”를 기록해야 한다.

---

## 8. Raw Log와 Injected Context 분리

원본 대화 기록과 API 요청 맥락은 분리한다.

```text
Raw Conversation Log
= 원본 기록
= 감사, 재현, 검색, 디버깅용

Injected Context
= API 요청에 실제 포함된 맥락
= Context Builder가 조립
```

모든 원본 대화는 저장한다.
하지만 과거 전체 원문을 매 요청마다 전송하지 않는다.

---

## 9. Summary + Window 원칙

LLM IDE의 기본 장기 대화 관리 전략은 `Summary + Window`다.

```text
Raw Conversation Log
+ Rolling Context Summary
+ Recent Window
```

### Rolling Context Summary

과거 대화 맥락을 압축한 요청 주입용 요약이다.

* LLM Provider API로 생성한다.
* 원본 대화 로그를 대체하지 않는다.
* 다음 chat 요청에 과거 맥락으로 포함한다.
* 압축 실패 시 기존 Summary를 유지한다.

### Recent Window

최근 N개의 user/assistant 대화를 원문으로 유지하는 제한된 대화 창이다.

* 직전 흐름 유지
* 지시어 참조 유지
* 말투와 형식 유지
* 짧은 문맥 연속성 보장

Sliding Window는 Recent Window 구현에만 사용한다.
RAG는 MVP에서 제외하고 File Store 이후 검토한다.

---

## 10. Criteria 우선 원칙

Criteria는 프로젝트 기준이다.

활성 Criteria는 API 요청에 포함되어야 한다.
비활성 Criteria는 요청에 포함하지 않는다.

AI 응답은 활성 Criteria를 따라야 한다.

Criteria는 Rolling Context Summary보다 우선한다.
압축 요약이 Criteria와 충돌하면 Criteria가 우선한다.

---

## 11. Project State 우선 원칙

Project State는 사용자가 승인한 현재 프로젝트 상태다.

Project State는 다음 정보를 관리한다.

* Stage
* Current Task
* Completed Items
* Next Actions
* Blockers

Project State는 압축 요약보다 우선한다.
AI가 상태 변경을 제안할 수는 있지만, 사용자 승인 없이 Project State를 변경할 수 없다.

---

## 12. Agent Boundary Principle

LLM IDE는 에이전트 기능을 수용할 수 있는 구조로 설계한다.
그러나 MVP에서는 자율 실행 에이전트를 구현하지 않는다.

AI는 다음을 할 수 있다.

* 응답 생성
* 요약
* 상태 변경 후보 제안
* 산출물 초안 생성
* 파일/맥락 기반 분석

AI는 사용자 승인 없이 다음을 할 수 없다.

* Project State 변경
* Criteria 변경
* Artifact 확정 저장
* 파일 수정
* 프로젝트 삭제
* 외부 명령 실행
* 다음 작업 자동 실행

LLM IDE는 AI가 작업을 제안하고 사용자가 승인하는 구조를 기본으로 한다.

---

## 13. Artifact 승인 원칙

Artifact는 중요한 AI 응답 또는 사용자가 보존하려는 산출물이다.

AI는 Artifact 후보를 제안할 수 있다.
하지만 사용자 승인 없이 Artifact를 확정 저장하지 않는다.

원본 chat 응답은 그대로 대화 로그에 남긴다.
Artifact는 원본 응답에서 분리된 재사용 가능한 산출물이다.

---

## 14. Provider 분리 원칙

IDE Core는 특정 LLM Provider에 종속되지 않는다.

Provider는 교체 가능한 어댑터로 구현한다.

MVP의 첫 Provider는 DeepSeek이다.
하지만 Core는 DeepSeek 전용 구조가 되어서는 안 된다.

```text
Core
→ Provider Interface
→ DeepSeek Provider
→ Future Providers
```

---

## 15. CLI 우선 원칙

MVP는 CLI 기반으로 구현한다.

WPF GUI는 후속 단계에서 적용한다.

```text
MVP = CLI 기반 구현
차기 단계 = WPF GUI 적용
```

모든 핵심 기능은 CLI 환경에서 먼저 검증한다.
WPF는 동일한 Core 라이브러리를 사용하는 UI 계층으로 추가한다.

---

## 16. Core 중심 원칙

비즈니스 로직은 Core에만 존재한다.

```text
LlmIde.Core
= 비즈니스 로직

LlmIde.Cli
= Core 호출 어댑터

LlmIde.Wpf
= Core 호출 UI

LlmIde.Server
= Core 호출 로컬 서버 어댑터
```

CLI, WPF, Server는 동일한 Core 서비스를 사용해야 한다.

---

## 17. 추적 가능성 원칙

LLM IDE는 다음을 추적해야 한다.

* 어떤 요청이 실행됐는가
* 어떤 Provider와 Model을 사용했는가
* 어떤 Criteria가 포함됐는가
* 어떤 Project State가 포함됐는가
* 어떤 Rolling Context Summary가 포함됐는가
* 어떤 Recent Window가 포함됐는가
* 어떤 Artifact가 첨부됐는가
* 어떤 파일이 첨부됐는가
* 어떤 응답이 생성됐는가
* 어떤 압축 요청이 실행됐는가

LLM IDE의 응답은 재현 가능하고 감리 가능해야 한다.

---

## 18. 실패 격리 원칙

보조 작업 실패가 본 작업을 망치면 안 된다.

예를 들어 Compression Request가 실패해도:

* 사용자 응답은 유지한다.
* Raw Conversation Log는 유지한다.
* 기존 Rolling Context Summary는 유지한다.
* 실패 상태를 Request Log에 기록한다.

압축 실패는 chat 실패가 아니다.

---

## 19. 파일 관리 원칙

File Store는 프로젝트 파일을 AI 맥락으로 활용하기 위한 기능이다.

MVP에서는 다음까지만 구현한다.

* 파일 등록
* 텍스트 추출
* 파일 요약
* 명시적 첨부

RAG 기반 검색은 MVP 범위에서 제외한다.
Vector DB와 Embedding 기반 검색은 File Store 안정화 이후 검토한다.

---

## 20. 사용자 최종 권한 원칙

사용자가 프로젝트 기준과 상태 변경의 최종 권한자다.

AI는 제안할 수 있다.
IDE는 기록하고 추적할 수 있다.
하지만 확정은 사용자가 한다.

```text
AI는 제안한다.
IDE는 기록한다.
사용자가 승인한다.
```

---

## 21. 제품 한 줄 정의

```text
LLM IDE는 stateless LLM 위에 stateful project runtime을 얹어,
프로젝트 기준, 상태, 맥락, 산출물을 관리하고
매 요청마다 필요한 맥락을 AI에게 주입하는 자연어 IDE다.
```
